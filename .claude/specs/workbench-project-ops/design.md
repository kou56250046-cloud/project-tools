# 案件ワークベンチ 案件の操作 — 設計

## データ構造

### 取り消しの段（store、メモリのみ）
```ts
undoById: Map<projectId, UndoStep[]>   // 新しいものが末尾。最大 UNDO_LIMIT = 20
type UndoStep = { ledger: Ledger /* 適用前の台帳 */; at: string; source: string; label: string; count: number };
```
- 今の `undoLedger`（1 段）を置き換える。`canUndo()` は段があるか、`undo()` は末尾を1つ戻す
- `label` と `count` は、適用後の changelog の最後の記録から作る（種類の決め方は末尾の「取り消しの段の source」、件数は changes の数）
- `undoTo(i)`: 数え方は末尾の「undoTo の数え方」
- 書き出し状態: 戻した結果の revision が書き出した revision より小さければ、未書き出しにする（日時の扱いは末尾の「書き出しの日時」）

### リセット（store.resetProject(starterId)）
- `createLedger(name, starterId, now)` で新しい台帳を作り、元の台帳から project（starter は選び直した値）と settings を移す
- revision = 元の revision + 1。changelog は空にしてから `{ op: 'reset' }` の記録を1件足す
- 取り消しの段に元の台帳を積む（AC-04）。persist・emit('apply')

### 合言葉の変更（store.changePassphrase(current, next)）
1. 箱の salt と回数で `deriveKey(current)` → 箱を開けてみる。失敗 → `{ ok: false, error: '今の合言葉が違います' }`
2. 新しい salt と鍵を作り、workspace と退避データをそれぞれ暗号化した文字列を先に作る（ここまでで localStorage は変えない）
3. 両方そろったら localStorage の箱と退避を書き換え、store.key / salt を新しいものにする（書き込みの失敗時は末尾の「2 つのキーの部分失敗」）
4. 2 で例外 → 何も書き換えずに失敗を返す（AC-08）
- 書き込みの直列化: 末尾の「合言葉の変更の直列化」（保存の鎖の中で 1〜3 を行う）

### 上部の「＋ 新しい案件」
- `newProjectDialog()`（lock.js の askNewPassphrase と同じ作りのダイアログ。dom.js に置く）: 案件名と型 → 作る / やめる
- 作るとき `ensureVaultReady()` → `store.addProject(createLedger(...))`

## 画面
- 上部: 「＋ 新しい案件」（案件名の横）、「取り消し」「履歴」（書き出しの左）
- 履歴: ダイアログで直近の段を新しい順に表示。各行に「ここまで戻す」。確認「この変更の前まで戻します。それより後の N 件の変更は失われ、やり直せません」
- 設定: 「この案件」の欄に「中身を空に戻す」（型の選択つき）。「合言葉を変える」の欄（3 つの入力と変えるボタン）

## 検討した代替案
| 案 | 採らなかった理由 |
|---|---|
| 取り消しの段を暗号化して保存 | 保存量が 20 倍になり、5MB の上限に近づく。再読み込みで消えることを使い方に書く |
| changelog から逆算して戻す | 記録は「何が変わったか」だけで元の値を持たない。台帳の写しを持つ方が確実 |
| リセットで新しい案件を作り直す（ID も新しく） | 横断や書き出し状態の対応が切れる。同じ案件の中身だけを入れ替える |
| 合言葉の変更で、新しい箱を書いてから古い箱を消す | 1 つのキーの上書きは原子的なので、同じキーへの上書きで足りる。キーは 2 つあるので、元の暗号文を取っておき、失敗したら両方書き戻す |

## レビューを受けて決めたこと

### 合言葉の変更の直列化（指摘1）
- `changePassphrase` 全体を `this.saving = this.saving.then(...)` の鎖に入れる。鎖の中で、今の箱を開けて確かめる → 新しい鍵を作る → その時点の workspace と退避を暗号化 → 書き込み → `this.key` / `this.salt` の差し替え、までを行う。後から呼ばれた persist は鎖の後ろに並ぶので、差し替え後の鍵で書く
- persist は鍵を「呼ばれた時点」ではなく「鎖の中で実行する時点」で読むように直す（鎖に並んだ古い persist が古い鍵で書かないように）
- 実行中は設定画面の「変える」ボタンを押せなくし、「変えています…」と出す。ほかの操作は止めない（上の直し方で安全）

### 2 つのキーの部分失敗（指摘2）
- 書き込みの前に、今の vault と recovery の文字列（暗号文）を手元に取っておく
- vault → recovery の順に書き、どちらかで lsSet が false を返したら、両方を取っておいた文字列に書き戻し、鍵は差し替えずに `{ ok: false, error: '保存に失敗しました（容量不足の可能性）。合言葉は変わっていません' }` を返す

### 開けない退避（指摘3）
- 合言葉の変更の前に、localStorage に退避があるのにメモリの recovery が空（＝今の合言葉で開けない退避がある）なら、変更を止めて「開けない退避データがあります。先に設定から消すか、元の合言葉で開いて書き出してください」と出す。退避が無いときは recovery のキーに触らない

### 取り消しの段の source（指摘5）
- 段の表示は `changes[0].op` が settings / baseline / reset ならそれを、そうでなければ記録の source（import / local / hearing）を使う。commitExternal の source は変えない（書き出した台帳の形を変えないため）

### undoTo の数え方（指摘6）
- 段の配列は古い順。`undoTo(i)`: 配列の i 番目の ledger に戻し、i 番目を含めそれ以降をすべて捨てる。失われる変更の数 N = 配列の長さ − i。履歴の表示は新しい順に並べ替えて出すが、ボタンには配列の i を持たせる

### リセットと取込の下書き（指摘7）
- resetProject は token を変え（取込の下書きを捨てる）、selectedId を null にする。undo / undoTo は今と同じく gen だけ上げる（同じ案件の台帳の変化なので、下書きは検証し直す）

### 書き出しの日時（確認事項8への判断）
- 書き出しより前に戻ったときは revision だけを消し、日時は残す（「最後の書き出し」の日時は事実として正しいため）。undo の既存の動きもこれに合わせて直す

### 別のタブ（確認事項9への判断）
- 非目標とし、使い方の「合言葉を変える」の説明と設定画面に「同じツールを別のタブで開いているときは、先に閉じてください」と書く

### 台帳が無いときの「＋ 新しい案件」（確認事項10への判断）
- 台帳が無いとき（合言葉を決める前を含む）も出す。押すと ensureVaultReady で合言葉を決めてから作る。ようこそ画面の文言も「上の『＋ 新しい案件』か『設定』から」に直す

### 取り消しの段の大きさ（確認事項11への判断）
- 制約の「数 MB 以内」は目安とし、T1 のテストで 500 項目の台帳の JSON の長さを測り、×20 が 20MB 未満であることを確かめる（メモリの話で localStorage の上限とは別）
